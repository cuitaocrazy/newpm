# 行为契约：删除日报

**Feature**: 015-daily-report-ownership-check
**接口**: `DELETE /project/dailyReport/{reportIds}`
**权限**: `project:dailyReport:remove`（既有，不变）
**审计**: `@Log(title="日报管理", businessType=DELETE)`（既有，不变）

> 本契约**不改变**请求／响应结构，只改变**行为语义**。前端零改动。

## 核心语义变更

### 变更前

> 「删除这条日报」——物理删除该日报的全部明细，软删除主记录。

后果：填报人在界面上看不到的工时（如已结项项目的历史工时）被连带删除。

### 变更后

> 「删除这条日报中**填报人能看到的**部分。看不到的部分保留；只要还有保留的部分，主记录也保留。」

**业务依据**（业务方 2026-07-30 确认）：项目结项后虽不再显示在日报界面中，但此前已填写的日报数据
必须保留——不能因为填报人在日报上执行了删除操作，就把已结项项目的工时无辜删掉。

## 行为矩阵

| 该日报的明细构成 | 明细结果 | 主记录结果 | 当日汇总工时 |
|---|---|---|---|
| 全部为可见项目工时 / 假期 | 全部删除 | **软删除**（既有行为） | — |
| 含不可见项目工时（如已结项） | 仅删可见部分，**不可见部分原样保留** | **保留** | **按剩余 work 明细重算** |
| 全部为不可见项目工时 | 全部保留 | 保留 | 保持不变 |

## 不变式（实现必须保证）

- **INV-D1**：不存在「有工时明细但其主记录已被软删」的孤立数据——被保留的明细必须始终可通过
  日报查询到达（对应 SC-010）
- **INV-D2**：主记录被保留时，其当日汇总工时严格等于剩余 `work` 类型明细的工时之和
- **INV-D3**：被保留明细的工时数、工作内容、所属任务、工作类别在删除操作前后逐字节相同
- **INV-D4**：删除操作完成后，涉及项目的实际人天严格等于其全部日报明细的工时汇总
  （沿用 Issue #5 的对账口径）
- **INV-D5**：当该日报所有明细都在可见范围内时，行为与变更前完全一致（不引入回归）

## 填报人视角的表现

删除后重新打开该日期：

- 若已无任何记录 → 与变更前一致（日报不存在）
- 若仍有不可见工时被保留 → 填报人**看到的仍是空白**（那些工时本来就不在他的可见范围内），
  但日历卡上该日仍会显示汇总工时（来自主记录的当日汇总）

> ⚠️ 这一点会让填报人产生轻微困惑：「我删了，为什么日历上还有工时？」
> 属**已知的可接受折中**——相比静默丢失他人／历史工时，宁可让填报人看到一个无法解释的残留数字。
> 若需彻底消除困惑，应走「让已结项项目在填写页以只读行呈现」的体验增强路线（不在本特性范围）。

## 兼容性

| 调用方 | 影响 |
|---|---|
| 桌面填写页 / 移动端 H5 的删除入口 | 无需改动；仅当该日报含不可见工时时行为不同 |
| 直接调用 API 的脚本 | 若曾依赖「删除后该日报彻底消失」，在含不可见工时的日报上不再成立 |
