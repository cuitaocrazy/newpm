# Feature Specification: 项目日报的人员可见性与口径自证

**特性分支**: `018-project-daily-report`
**创建日期**: 2026-08-03
**状态**: 需求已确认（6 项澄清全部拍板）
**依赖**: 本特性基线挂在 `015-daily-report-ownership-check` 之上（HEAD `d269536`）。**015 必须先合并 main，018 才能合。**

> 数据说明：本文中所有绝对计数均取自**本地 docker 库 `newpm-mysql-1` / `ry-vue` 的 2026-08-03 快照**，口径 `del_flag='0'`。该库在勘察期间仍被 e2e 造数写入，计数会小幅漂移（已实测：有效项目 283→284、distinct 日报日 180→181）。**判定性结论**（如「取 ancestors 末段不可能产出深圳组」）不受漂移影响，**精确计数**仅作量级参考，生产分布须另行核查。

## 背景

「项目日报」（页面 `ruoyi-ui/src/views/project/dailyReport/teamReport.vue`，组件名 `TeamDailyReport`，本地菜单 `menu_id=2220` 已名为「项目日报」，但种子 SQL `pm-sql/init/02_menu_data.sql:287` 仍写「团队日报」）是**以项目为维度**的日报视图：一行一个项目，纵向展开该项目的参与人员，横向铺开当月每一天的工时，右侧给出项目累计人天与预算人天。它服务于项目经理与部门管理者，回答的问题是「**这个项目的人天花在谁身上、花得对不对**」。

当前该页面存在两类问题。

### 一、有人天，却看不到承载它的人

右侧「实际人天」取自 `pm_project.actual_workload`，是**全周期**口径（`DailyReportMapper.xml:518`）：

```sql
ROUND(p.actual_workload / 8, 3) + COALESCE(p.adjust_workload, 0) AS actualPersonDays
```

而中间的人员行与日历格受**当月**月窗约束（`DailyReportMapper.xml:564-565`、`:585-586`）。两个口径不一致，直接后果是**同一屏内对不上账**：

- 2026-07 快照下，「项目累计人天 > 0」的 **183 个项目中有 67 个（37%）** 当月没有任何在册成员填过本项目日报 —— 表格上挂着人天，却找不到任何贡献者。
- 典型案例 `project 38`（兵团人社全程电子化）：全周期只有曲君（现 `is_active=0`）填过 166h，查 2026-07 时他不出现，页面只剩 3 个从未填报的在册成员空行，而 66.750 人天孤零零挂在右侧。

根因是离场成员分支（`DailyReportMapper.xml:559-574`）刻意只取「**本月**有工时」的人。该取舍在注释中写明是为「避免给所有项目凭空加行」，在按月浏览的原始设计下成立，但它让「累计人天」永远缺少解释。

### 二、年月被强制必填，无法看项目全貌

`teamReport.vue:293-296` 强制要求选择年月，而 SQL 中 `#{yearMonth}` 的 4 处引用（`:564-565`、`:585-586`）全部**没有 `<if>` 守卫**。这意味着即便前端放开，直接传空也不是「查全周期」而是**静默降级为空**：

```sql
-- 实测：SELECT STR_TO_DATE(CONCAT(NULL,'-01'),'%Y-%m-%d') → NULL
-- 日期比较全为 NULL → daily_hrs 与离场分支双双返回 0 行
```

表现为「所有人 0 工时 + 离场成员凭空消失」。所以「年月非必填」不是删掉一个前端校验就能达成的。

### 三、口径不可自证

「实际人天」这个列名既不说明它是**累计**的（用户容易误读为「本月实际」），也不说明它**含补正天数**。页面上没有任何地方解释它怎么算出来的，而它恰恰是本页最重要、也最容易被质疑的数字。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 项目的人天必须有人承载 (Priority: P1) 🎯 MVP

**作为**项目经理，**我希望**凡是给本项目填过日报的人（包括已被移出项目组、已离职的人）都出现在人员列表中，**以便**右侧的项目累计人天有据可查，而不是一个无法解释的孤立数字。

**为什么是 P1**：这是本次改造要解决的核心痛点，37% 的项目当前处于「对不上账」状态。其余需求都是在此基础上的可读性增强。

**独立验收**：单独交付本条即可让 67/183 个「有人天无贡献者」的项目恢复可解释性。

**验收场景**：

1. **假如** `project 38` 全周期只有曲君填过工时（166h）且他现已被移出项目组，**当** 项目经理查询该项目（无论选不选年月），**那么** 曲君出现在人员列表中、灰显并标注「已离场」，其工时计入项目累计人天。
2. **假如** 某人从未以任何身份出现在 `pm_project_member`（哪怕曾给该项目填过日报），**当** 任何人查询该项目，**那么** 该人**不得**出现 —— 这是 015 建立的安全边界，见 US5。
3. **假如** 查询条件选定 2026-07，而某离场成员最后一次填报是 2026-03，**当** 查询执行，**那么** 该成员仍然出现（整行日历为空），因为他的工时在右侧累计人天里。

### User Story 2 - 不限定月份查看项目全貌 (Priority: P1)

**作为**部门管理者，**我希望**不选年月也能查询，看到项目从开始到最新一天的累计情况，**以便**评估项目整体投入而不必逐月翻查。

**为什么是 P1**：与 US1 同为「看全貌」诉求的两面，且 US1 的全周期人员展示在不填年月时才完全自洽。

**独立验收**：单独交付本条即可支持「项目整体投入」这一独立分析场景。

**验收场景**：

1. **假如** 用户清空年月并选定项目所属部门，**当** 点击查询，**那么** 查询成功执行（不再弹出「请选择年月」），列表中**不出现任何日期列**。
2. **假如** 不填年月，**当** 结果返回，**那么**「项目累计人天」显示的仍是从项目开始到最新日报日的累计值 —— 该列本就与年月无关，不因是否填年月而变化。
3. **假如** 不填年月，**当** 结果返回，**那么**「个人人天」显示该成员在本项目的**全周期**人天（与项目累计人天同为全周期口径，同一屏内不混口径）。
4. **假如** 用户选定年月，**当** 结果返回，**那么** 日期列、日历格、个人人天恢复为该月口径 —— 现有行为不变。

---

### User Story 3 - 一眼看清每行是谁、项目挂在哪个机构 (Priority: P2)

**作为**项目经理，**我希望**人员列显示「昵称（角色）」、项目列显示所属机构分组，**以便**在不点开项目详情的情况下判断人员构成是否合理。

**独立验收**：纯展示增强，可在 US1/US2 之后独立交付。

**验收场景**：

1. **假如** 冯先勇在 `project 55` 中既是项目经理又在参与人员串里，**当** 查询该项目，**那么** 人员列显示「冯先勇（项目经理）」—— 按优先级取最高一个，不并列展示。
2. **假如** 某成员四个角色字段均不命中（如 e2e 造数的系统管理员行），**当** 查询，**那么** 人员列只显示昵称，不带括号。
3. **假如** `project` 的 `project_dept` 指向「深圳组」（`dept_id=216`，叶子部门），**当** 查询，**那么** 项目列在「确认」金额行下方新增一行显示「深圳组」。
4. **假如** 某项目的 `project_dept` 指向非叶子部门（如「项目五组（科技项目外派）」），**当** 查询，**那么** 显示该部门自身的名称 —— 粒度较粗但不是错误。

---

### User Story 4 - 累计人天的算法可自证 (Priority: P2)

**作为**被质疑数字的项目经理，**我希望**页面上直接写明累计人天怎么算出来的，**以便**不必翻代码或找开发解释。

**独立验收**：纯文案，随时可独立交付。

**验收场景**：

1. **假如** 用户打开页面，**当** 视线落在查询条件与列表之间的图例区，**那么** 能读到「项目累计人天 = 项目日报小时 ÷ 8 + 补正天数」。
2. **假如** 表头已改名为「项目累计人天」，**当** 用户对照图例，**那么** 图例中的红色告警说明使用的是**同一个名字**，不出现「实际人天」与「项目累计人天」指同一列却两种叫法的情况。

---

### User Story 5 - 安全边界不因可见性放宽而松动 (Priority: P1，回归保护)

**作为**系统的安全责任人，**我希望**「参与过」的判据始终是「曾在 `pm_project_member` 留下过行」，**以便**没有人能通过给任意项目填 0.01 小时来自助获得可见身份，进而读取该项目的预算/合同金额/收入确认金额。

**为什么是 P1**：US1 的字面表述（「写过本项目日报的都要显示」）极易被实现成「去掉曾是成员的门槛」。本条是防止该误读落地的显式约束。

**验收场景**：

1. **假如** 某账号从未在 `pm_project_member` 中出现于项目 X，**当** 它以任何方式给项目 X 提交工时后再查询，**那么** 它**不得**出现在项目 X 的人员列表中。
2. **假如** 既有 e2e 安全用例 `tests/e2e-team-daily-workload.spec.js:227-282` 运行，**那么** 它必须保持通过。

---

### Edge Cases

- **项目无任何成员且无任何日报**：保持现有占位行行为（`teamReport.vue:247-262`），人员列显示「—」。
- **离场成员在 `leave_date` 之后仍有日报**：实测存在 2 对（如 `project 17` 游生寿 `leave_date=2026-03-04` 但日报到 2026-06-24）。参与时间按日报首末日展示，故该情形自然呈现为「参与到 2026-06-24」，不做特殊处理也不报错。
- **在册成员从未填过任何日报**：无日报首末日可取，回退展示 `join_date ~ leave_date`（`leave_date` 为空时展示为「join_date 起」）。
- **不填年月时表格退化为 5 列全 fixed（2 左 + 3 右）、中间可滚动区为 0 列**：布局表现需实跑验证；若异常，按 `:fixed="dayColumns.length ? 'right' : false"` 处理。
- **`project_dept` 为空或指向已删除部门**：实测 284 个有效项目中 0 空值、0 孤儿，但实现仍须容忍 NULL（显示「—」而非报错）。

## Requirements *(mandatory)*

### Functional Requirements

**人员可见性（US1 / US5）**

- **FR-001**: 项目的人员列表 MUST 包含两类人：(a) 当前在册成员（`is_active='1' AND del_flag='0'`）；(b) 曾是该项目成员且给该项目填过 `entry_type='work'` 日报的人，**不限时间**。
- **FR-002**: (b) 类人员的准入判据 MUST 保留「曾在 `pm_project_member` 存在过任意状态的行」这一约束（现 `DailyReportMapper.xml:566-569` 的 `EXISTS`）。该约束 MUST NOT 因本特性被删除或放宽。
- **FR-003**: (b) 类人员的展示 MUST 沿用现有的灰显 + 「已离场」标签，且其工时 MUST 继续计入项目累计人天。
- **FR-004**: 无论查询是否指定年月，(b) 类人员的取数范围 MUST 一致（均为全周期），不得出现「按月查看不见、不按月查看得见」的行为差异。
- **FR-005**: 离职人员（`sys_user.status='1'`，昵称含「（已离职）」后缀）MUST 与在职人员同等对待 —— 现有 `INNER JOIN sys_user` 不带 status 过滤，本特性 MUST NOT 新增该过滤。

**年月非必填（US2）**

- **FR-006**: 年月 MUST 改为非必填。前端 MUST 移除必填校验；项目所属部门的必填校验保留。
- **FR-007**: 未指定年月时，SQL MUST 跳过全部月窗条件（4 处），而非传入空值触发静默降级。
- **FR-008**: 未指定年月时，查询结果 MUST NOT 包含任何日期维度数据（`report_date`），前端据此渲染 0 个日期列。
- **FR-009**: 未指定年月时，「个人人天」MUST 退化为该成员在本项目的全周期工时合计 ÷ 8。
- **FR-010**: 「项目累计人天」的取值 MUST 保持为 `ROUND(actual_workload/8,3) + COALESCE(adjust_workload,0)`，不因是否指定年月而改变计算方式。**MUST NOT** 改为查询期实时 SUM。

**展示增强（US3 / US4）**

- **FR-011**: 人员列 MUST 显示为「昵称（角色）」。角色由 `pm_project` 的 `project_manager_id` / `market_manager_id` / `sales_manager_id` / `participants` 四字段在查询期反推，命中多个时按 `项目经理 > 市场经理 > 销售负责人 > 参与人员` 取最高一个。
- **FR-012**: 反推不出任何角色时，人员列 MUST 只显示昵称，不带空括号。
- **FR-013**: 项目列 MUST 在「确认」金额行下方新增一行，显示 `pm_project.project_dept` 对应的 `sys_dept.dept_name`（部门自身名称，不是路径、不是 ancestors 末段）。
- **FR-014**: FR-013 的新字段 MUST 使用独立别名（如 `projectDeptName`），MUST NOT 复用现有 `deptName` —— 后者是**成员本人**部门，实测 38% 与项目部门不同。
- **FR-015**: 表头「实际人天」MUST 改为「项目累计人天」。图例中指代该列的文案 MUST 同步改名。
- **FR-016**: 图例区 MUST 在现有三条之后追加一条备注：「项目累计人天 = 项目日报小时 ÷ 8 + 补正天数」。
- **FR-017**: 人员移出项目组后，其参与本项目的时间 MUST 在人员列体现。口径为该人在本项目的日报首末日（`MIN/MAX(report_date)`）；无日报时回退展示 `join_date ~ leave_date`。

**措辞与导航（US3）**

- **FR-018**: 查询条件「项目部门」的标签 MUST 改为「项目所属部门」。
- **FR-019**: 项目名称 MUST 支持右键「在新标签页打开」查看项目详情，实现方式为真实 `<a href>` + `@click.prevent` 走前端路由（与 `stats.vue:35-40` 一致）。

**不在本特性范围（显式排除）**

- **OUT-001**: `@DataScope` 的绑定语义（现绑成员本人部门而非项目部门）不改。相关差异记为已知限制，另开 Issue。
- **OUT-002**: `selectTeamProjectOptions`（项目名下拉，`DailyReportMapper.xml:485-510`）硬编码 `is_active='1'` 不改。全员已离场的项目在下拉中搜不到，记为已知限制。
- **OUT-003**: 不新增 `pm_project_member.member_role` 列。落库角色对存量数据零收益（已离场的 9 行照样推不出），只对未来数据有效，改动面却横跨 `syncProjectMembers` 全链路。

### Key Entities

| 实体 | 本特性中的角色 | 关键字段 |
|---|---|---|
| `pm_project` | 项目主体；角色反推与机构分组的数据源 | `project_dept`、`project_manager_id`、`market_manager_id`、`sales_manager_id`、`participants`、`actual_workload`、`adjust_workload`、`estimated_workload` |
| `pm_project_member` | 成员准入判据与参与时间兜底源 | `project_id`、`user_id`、`join_date`、`leave_date`、`is_active`、`del_flag` |
| `pm_daily_report` + `pm_daily_report_detail` | 工时与参与时间的主源 | `report_date`、`project_id`、`work_hours`、`entry_type` |
| `sys_dept` | 机构分组名称 | `dept_id`、`dept_name`（注意 collation 差异，见 plan） |
| `sys_user` | 人员昵称与离职标记 | `nick_name`、`status` |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 2026-07 快照下「有累计人天但当月无任何贡献者」的项目数从 **67 个降至可解释状态** —— 即这些项目在查询后至少显示一个有工时的人员行（在册或离场）。
- **SC-002**: 全周期离场且填过本项目日报的 **11 对 (项目,人)** 在查询结果中全部可见（月窗放宽前为 1 对）。
- **SC-003**: 「写过 work 日报但从未在 `pm_project_member` 出现」的人员在结果中的数量保持为 **0**（改动前后一致），且 `tests/e2e-team-daily-workload.spec.js:227-282` 安全用例保持通过。
- **SC-004**: 不填年月执行查询，返回结果中日期列数为 **0**，且「项目累计人天」与填年月时的值**逐项目相等**（该列与年月无关）。
- **SC-005**: 不填年月时的查询原始行数控制在 **2199 行量级**（现状带月窗 4642 行），不出现 16111 行（去月窗但保留 `report_date` 分组）的爆炸形态。
- **SC-006**: `selectTeamMonthly` 的单测覆盖从 **0 个方法**提升到覆盖本特性全部改动路径（月窗条件化、角色反推、参与时间回退、机构分组）。
- **SC-007**: `mvn test -pl ruoyi-project -am` 全量通过，数量不低于改动前基线（015 记录为 192）。
- **SC-008**: 页面上「项目累计人天」这一列的名称在表头与图例中**完全一致**，全页搜索不到指代该列的「实际人天」字样。

## Assumptions

1. **015 会先合并 main**。本特性的安全前提（`saveDailyReport` 已有「曾以任意身份参与过该项目」的写入侧校验）来自 015。若 015 未合并，FR-002 的 `EXISTS` 从「纵深防御第二道」退回「唯一防线」，语义不变但注释描述需相应调整。
2. **「深圳租」是「深圳组」的笔误**。依据：`dept_id=216` 名为「深圳组」、叶子部门、`ancestors='0,100,101,105,208'`，与需求举例一字之差且语境完全吻合；数据库中不存在名为「深圳租」的部门。
3. **`team_leader_id` 不参与角色反推**。实测 284 个有效项目中 100% 为 NULL，该档位永远不命中。若未来该字段启用，需回头补入优先级链。
4. **「销售负责人」是正确叫法**。依据 DB 注释与前端 label（`project/edit.vue:285`），不是「销售经理」。
5. **多角色是代码行为而非脏数据**。`ProjectMemberServiceImpl.java:73-79` 在同步成员后把整个成员集合回写 `pm_project.participants`，导致经理们也进了 participants（实测 21.8% 命中 2 个以上角色）。优先级链把经理排在参与人员之前正是为了抵消这一副作用，**不应把它当脏数据去「修」**。
6. **默认年月保留为当月**。用户主动清空才走全周期，避免首屏就触发全周期查询。
7. **菜单已改名，无需再改**。用户于 2026-08-03 确认：生产 <https://newpm.yadashuke.com/dailyReport/teamReport> 的菜单已从「团队日报」改为「项目日报」；本地 `menu_id=2220` 亦已是新名。**但种子 SQL `pm-sql/init/02_menu_data.sql:287` 仍写「团队日报」**，需同步改名，否则新环境初始化会退回旧名。路由 `path` 与组件名 `teamReport` / `TeamDailyReport` 保持不变（改动收益为零、风险不小：会使既有书签、`sys_menu.component` 记录、e2e 选择器全部失效）。
