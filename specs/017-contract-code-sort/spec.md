## 一、业务描述

合同管理与付款里程碑是合同款项模块的两个主查询列表：

- **合同管理**（`/htkx/contract`）：合同台账，业务人员按部门、类型、状态查合同及其关联项目、金额、收入确认情况
- **付款里程碑**（`/htkx/payment`）：以合同为单位展开其下的各期付款里程碑，跟踪开票、回款季度与实际回款

使用者是合同与财务口的业务人员。合同编号（`pm_contract.contract_code`）是合同的业务主键，形如 `YD-BOC-KF-2026-RJ02-0007`，其中编码规则本身带有单位、年份、类型等含义，**按编号排序等价于按编码规则分组浏览**，是对账和批量核查时的高频需求。

两个列表数据量均为数百条（实测合同 307 条、付款里程碑 478 行），**均由后端分页**，每页 10 条。

## 二、期望行为

用户点击「合同编号」表头，列表按合同编号排序；再次点击反向排序；第三次点击取消排序回到默认顺序。排序作用于**全部数据**，而非当前页。

## 三、功能需求

| 编号 | 需求 |
|---|---|
| FR-001 | 合同管理列表的「合同编号」列表头显示排序图标，可点击排序 |
| FR-002 | 付款里程碑列表的「合同编号」列表头显示排序图标，可点击排序 |
| FR-003 | 点击表头按「升序 → 降序 → 取消排序」三态循环 |
| FR-004 | 排序为**后端全局排序**：请求携带 `orderByColumn=contract_code` 与 `isAsc`，由后端对全量数据排序后再分页；不得是前端对当前页重排 |
| FR-005 | 取消排序后回到该列表原本的默认排序 |
| FR-006 | 排序与既有查询条件叠加生效，排序不改变筛选结果的范围 |
| FR-007 | 翻页时保持当前排序 |
| FR-008 | 合同编号为空的记录参与排序，不被丢弃 |

## 四、不变式（排序不得破坏的既有行为）

| 编号 | 不变式 | 背景 |
|---|---|---|
| INV-1 | 付款里程碑排序后，同一合同的多条付款里程碑仍聚为一条记录 | 该查询是「合同 1:N 付款」的嵌套 `resultMap`（`ContractMapper.selectContractWithPaymentsList`），前端用 `spanMethod` 合并合同列的单元格。若排序把同一合同的多行打散，合并显示会错乱 |
| INV-2 | 「合计」行始终固定在列表首行，不参与排序 | 两页的合计行均由前端 `computed` 以 `[summary, ...list]` 拼接（`contract/index.vue:440`、`payment/index.vue:378`），与后端排序无关 |
| INV-3 | 排序参数不得成为 SQL 注入入口 | `orderByColumn` 是拼进 `order by` 的用户可控字符串 |
| INV-4 | 分页与排序叠加时不出现跨页重复或遗漏 | 排序键存在大量重复值（空编号）时，分页边界可能不稳定 |

## 五、超出范围

- 不改变两个列表的默认排序规则
- 不为其他列新增排序能力
- 不改动后端：`orderByColumn` / `isAsc` 是 RuoYi 框架既有的分页排序参数，由 `PageUtils.startPage()` 交给 PageHelper 处理
- 「重置」按钮不清除排序状态——`resetQuery` 走 `proxy.resetForm("queryRef")`，只重置表单绑定字段，而 `orderByColumn` 不在查询表单内。此行为与合同管理页排序功能上线以来的既有表现一致，本次不做变更
