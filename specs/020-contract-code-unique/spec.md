## 一、业务描述

**这块功能在业务上是干什么的**

合同管理（`/htkx/contract`，`ContractController` → `/project/contract/**`）是合同款项模块的台账主表。`pm_contract.contract_code`（合同编号）是**合同在企业内部的业务主键**，形如 `4004-2024-1210-01-00018`、`YD-BOC-KF-2026-RJ02-0007`，编码规则本身带有单位、年份、类型等含义。它在系统内外承担三个角色：

1. **对外唯一标识**——与纸质合同、客户系统、财务系统对账时，人和系统都以这个编号互认；
2. **系统内检索键**——合同列表（`ContractMapper.xml:8` 的 `contractFilterConditions`）、付款里程碑、项目关联合同、收入确认页均支持按编号模糊搜索与排序（见 `specs/017-contract-code-sort`）；
3. **跨部门流转凭据**——一份合同由某个部门录入，但市场、财务、项目多方都会按编号引用它。

**谁在用**

- **合同录入人员**（各业务部门）：在 `contract/add.vue` 新建合同、`contract/edit.vue` 维护合同；
- **财务与合同管理岗**：按编号对账、核查回款；
- **项目经理**：从项目页关联合同（`bind-contract.vue`）后按编号追溯。

**期望的正确行为**

同一个合同编号在系统中**至多对应一份在用合同**。录入人员键入一个已被占用的编号时，系统应当当场拒绝并说明原因，而不是把两份同号合同一起存下去让下游去猜哪份是真的。

同时，合同编号在本系统中**从来就不是必填项**——存量数据里大量合同（框架协议、历史迁移数据、尚未拿到正式编号的在途合同）本就没有编号。因此「唯一」只能约束**填了编号的那部分**，不能演变成「强制所有合同都得有编号」。

## 二、现状问题

### 2.1 现象：两份同编号合同并存

生产 `pm_contract` 中曾同时存在两条 `contract_code = 4004-2024-1210-01-00018` 的在用合同：

| contract_id | 归属部门 | 录入人 | 客户 / 类型 / 状态 / 金额 / 签订日期 | 编号字面值 |
|---|---|---|---|---|
| 258 | 201 | A | 与 263 **完全相同** | `4004-2024-1210-01-00018`（23 字节） |
| 263 | 103 | B | 与 258 **完全相同** | `4004-2024-1210-01-00018` + 尾部 TAB（24 字节） |

两条记录的客户、合同类型、合同状态、金额、签订日期**全部相同**，由两个部门的两名人员分别录入 —— 这是**重复录入**，不是「同一编号的补充协议 / 变更单」这类合法业务场景。

258 已于 **2026-08-06** 由业务方软删（`del_flag='1'`）作为临时处置，但**产生这条脏数据的机制原封不动**，随时可再次发生。

值得注意的是 263 的编号末尾带一个 **TAB（`CHAR(9)`）**，字节长度 24 而非 23 —— 即便将来加了朴素的字符串相等约束，这一对也**不会**被判为重复。判重必须在归一化之后进行。

### 2.2 根因：四道防线全空

| 层 | 应有防线 | 实际状况 | 证据 |
|---|---|---|---|
| L1 前端规则 | 新增/编辑页对 `contractCode` 做唯一性校验 | **完全缺席**。`add.vue` 的 `rules` 里只有 `contractName / deptId / customerId / contractType / contractStatus / contractAmount` 六项，没有 `contractCode`；`edit.vue` 同构同缺 | `contract/add.vue:326-347`、`contract/edit.vue:346-367` |
| L1' 前端调用 | 调用已有的校验接口 | `checkContractCodeUnique` **定义了但零调用方**——`add.vue:272` 与 `edit.vue:290` 的 import 里只有 `checkContractNameUnique`；全 `ruoyi-ui/src` grep 零命中 | `api/project/contract.js:68`（定义）；两处 import |
| L2 服务端拦截 | `insertContract` / `updateContract` 内判重 | **从不判重**。`insertContract` 只校验「项目是否已关联其他合同」，`updateContract` 同理 | `ContractServiceImpl.java:152`、`:210` |
| L3 校验接口本身 | 精确判重 | 接口存在但**两个缺陷**（见 2.3） | `ContractServiceImpl.java:366` |
| L4 数据库约束 | 唯一索引兜底 | **生产表上没有** `uk_contract_code`。DDL 脚本 `pm-sql/init/00_tables_ddl.sql:636` 声明了它，生产与本地开发库均无 —— **schema 漂移** | DDL `:636` vs 实测 `SHOW INDEX` 只有 `PRIMARY` |

四层都空，等于合同编号从来没有被任何机制约束过。

### 2.3 现有 `checkContractCodeUnique` 的两个缺陷

即便前端明天就接上这个接口，也不能直接用：

**缺陷 A：模糊匹配导致误报**
`ContractServiceImpl.java:374` 走的是 `contractMapper.selectContractList(contract)`，而该语句复用的 `contractFilterConditions`（`ContractMapper.xml:9`）对 `contract_code` 是：

```xml
and c.contract_code like concat('%', #{contractCode}, '%')
```

后果：输入 `ABC` 会命中已存在的 `ABC-001`，被误报「编号已存在」。**这条模糊匹配是合同列表搜索功能的正确实现，不能改**，判重必须另起精确语句。

**缺陷 B：空编号被判为「不唯一」**
`ContractServiceImpl.java:368-370`：编号为 null 或 trim 后为空时直接 `return false`（= 不唯一）。生产 310 条合同中 **114 条编号为空**（NULL 81 / 空串 31 / 字面「无」2）。若前端无条件调用该接口，这 114 条合同**全部无法保存**，业务全线卡死。

### 2.4 现状数据分布（2026-08-06 生产实测）

| 口径 | 数量 |
|---|---|
| 在用合同（`del_flag='0'`） | **309** |
| 软删合同（`del_flag='1'`） | **28** |
| 编号有效（归一化后非空） | **196** |
| 编号为空串 `''` | **31** |
| 编号为字面「无」 | **2** |
| 编号为 `NULL` | **81** |

> ⚠️ **计数口径待核实**：编号分布四项合计 196+31+2+81 = **310**，与「在用 309」相差 1。合理推测是两次取数跨越了 258 被软删的时点（软删前 310 条在用 / 软删后 309 条）。该差异不影响任何判定性结论（「大量编号为空」「重复必须归一化后才看得见」都成立），但**落 DDL 变更前必须以当次实测为准重新点一遍数**。记为待确认项 OQ-1。

**关键约束：软删记录仍保留原编号。** 实测「软删记录与在用记录编号冲突」共 **5 组**（含一组一号三行）。这直接决定了本特性**不能使用裸唯一索引** —— `UNIQUE KEY (contract_code)` 会把软删行一起纳入约束，导致：

1. 上索引这一步就会因存量冲突直接 `ALTER` 失败；
2. 即使清干净，「删掉合同 A 后拿同一个编号重建合同 B」这个完全合法的业务动作会被 `1062` 拒绝。

## 三、术语与归一化口径（本特性的度量衡）

本特性的所有判断都建立在同一个 `normalize()` 定义上。该定义**必须在 Java、判重 SQL、数据库生成列三处逐字一致**，任何一处偏离都会造成「应用放行但数据库报 1062」或「数据库放行但应用误拦」的裂缝。

**normalize(code) 定义**

1. 删除字符串中**所有位置**的 TAB（`CHAR(9)`）、CR（`CHAR(13)`）、LF（`CHAR(10)`）；
2. 再去掉首尾空格；
3. 若结果为空串 `''` 或字面「无」，则视为**未填写**，取值为 `NULL`。

**判重比对**：对 normalize 后**非 NULL** 的值做**精确相等**比对（不是 `like`）。

**两条容易踩空的细节**

- **MySQL 的 `TRIM()` 只去空格，不去 TAB**，而 Java 的 `String.trim()` 去掉所有 `<= U+0020` 的字符（含 TAB）。SQL 侧必须**显式** `REPLACE` 掉 `CHAR(9)/CHAR(13)/CHAR(10)`，且建议写 `CHAR(9)` 而非 `'\t'` 字面量以避免转义歧义。现实中 `contract_id=263` 的尾部 TAB 就是这个差异的产物。
- **归一化不删除字符串中间的空格**。`ABC 001` 与 `ABC001` 是两个不同的编号，不判为重复。

## 四、功能需求

### 归一化与空值语义

- **FR-1**：系统 MUST 采用 §三 定义的 `normalize()` 作为合同编号的唯一比对口径，且在 Java、判重 SQL、数据库约束三处的实现 MUST 逐字一致。
- **FR-2**：合同编号 MUST 保持**非必填**。normalize 结果为 NULL 的合同 MUST 允许保存，且**允许任意多条并存**，彼此之间不构成重复。
- **FR-3**：新增或修改合同时，落库的 `contract_code` MUST 是 normalize 之后的值 —— normalize 为 NULL 时写入 `NULL`，非空时写入去掉 TAB/CR/LF 并去首尾空格后的干净字符串。系统 MUST NOT 再产生形如 `contract_id=263` 的尾部带 TAB 的记录。

### 校验接口（L1）

- **FR-4**：`GET /project/contract/checkContractCodeUnique` 在 normalize 结果为 NULL 时 MUST 返回 `true`（唯一 / 放行）。**这是对现有行为的破坏性反转**（现为 `false`），是让 114 条空编号合同能继续保存的前提。
- **FR-5**：该接口对非空编号 MUST 做**精确**比对，MUST NOT 复用 `contractFilterConditions` 的 `like` 模糊匹配。
- **FR-6**：判重范围 MUST 是**全局的**，不受调用者数据权限（`@DataScope`）限制。依据：实测重复的两条记录分属部门 201 与 103，任何按部门收窄的查询都看不见对方。
- **FR-7**：判重范围 MUST 仅包含**在用记录**（`del_flag='0'`）。软删记录不占用编号 —— 删掉一份合同后，其编号 MUST 可被新合同重新使用。
- **FR-8**：编辑场景传入 `contractId` 时，判重 MUST 排除该合同自身。

### 服务端硬拦截（L2）

- **FR-9**：`insertContract` 在 normalize 后编号非空且已被其他在用合同占用时，MUST 抛出 `ServiceException`，中止本次新增。
- **FR-10**：`updateContract` 同 FR-9，且 MUST 排除合同自身。
- **FR-11**：拦截 MUST 是**硬拦截**——MUST NOT 提供任何「确认后放行」「强制保存」的旁路参数或后门。
- **FR-12**：错误提示 MUST 让录入人员能自行判断下一步（至少说明「合同编号已存在」并回显冲突的编号），MUST NOT 向前端暴露异常堆栈或 SQL 片段。
- **FR-13**：合同编号判重 MUST 排在既有「项目已关联合同」校验**之后**执行。依据：`tests/006-code-review-fixes.spec.js:235` 断言的是 `msg` 含「已关联其他合同」，顺序前置会把该文案顶掉。

### 前端反馈（L3）

- **FR-14**：新增页与编辑页 MUST 在合同编号失焦（blur）与提交前调用校验接口，重复时在表单项下方给出内联错误并阻止提交。
- **FR-15**：前端 MUST 使用与后端一致的 normalize 结果做「是否为空」的短路判断与接口入参 —— 空编号 MUST NOT 发起校验请求，更不得提示「已存在」。
- **FR-16**：编辑页传给校验接口的 `contractId` MUST 在合同详情尚未加载完成时也能取到（路由参数兜底），否则合同会把自己判成重复。
- **FR-17**：MUST NOT 给 `contractCode` 添加 `required` 规则（与 FR-2 冲突，且会让 114 条空编号合同无法编辑保存）。

### 数据库约束（L4）

- **FR-18**：`pm_contract` MUST 具备一条**只约束在用记录归一化编号**的唯一约束，作为并发与旁路写入（直连 SQL、未来新入口）的最后兜底。
- **FR-19**：该约束 MUST NOT 是 `contract_code` 裸列唯一索引 —— 依据 §2.4 的 5 组软删冲突与「删除后编号可重用」的业务要求。
- **FR-20**：当兜底约束被触发（并发写入撞车）时，系统 MUST 转换为与 FR-12 同口径的业务提示，MUST NOT 把 MySQL `1062` 原始错误抛给用户。

## 六、验收标准

| 编号 | 可验收判据 | 验证方式 |
|---|---|---|
| SC-001 | 在用合同（`del_flag='0'`）中，normalize 后非空且重复的编号组数 = **0**，且此后无法通过应用层再造出重复 | 迁移前后各跑一次分组计数 SQL |
| SC-002 | 以一个已被占用的编号新增合同 → 返回 `code=500` 且 `msg` 含「合同编号已存在」，库中不新增记录 | E2E（自建两条同号合同验证拦截，自清理） |
| SC-003 | 编辑某合同时不改编号直接保存 → 成功（`code=200`），**不被自己判重** | E2E + `clear-field-guards-regression.spec.js` 保持绿 |
| SC-004 | 编号为空（NULL / `''` / `'无'` / 纯 TAB）的合同新增与编辑均成功，且校验接口对这四种输入均返回 `true` | 单测 + E2E |
| SC-005 | 输入 `ABC` 时，已存在的 `ABC-001` **不**触发「已存在」——精确匹配生效 | 单测 |
| SC-006 | `\tABC` 与 `ABC` 被判为**同一个**编号（重复） | 单测 + E2E |
| SC-007 | 跨部门重复可被检出：以部门 A 的账号新增一个已被部门 B 占用的编号 → 被拦截 | 单测（验证判重不经 `@DataScope`）+ 生产观测 |
| SC-008 | 编辑页清空合同编号并保存 → 库中该字段变为 `NULL`（INV-3） | E2E |
| SC-009 | `SHOW CREATE TABLE pm_contract` 含针对归一化编号的唯一约束；直接用 SQL 插入一条与在用记录同归一化编号的记录 → 报 `1062` | 手工 SQL 验证 |
| SC-010 | `mvn test -pl ruoyi-project -am` 全绿，且 `ContractServiceImplTest` 覆盖 normalize 的全部边界输入 | CI / 本地 |
| SC-011 | 指定回归套件全绿：`e2e-contract-crud`、`contract-filter`、`clear-field-guards-regression`、`guard-payload-runtime`（合同段）、`006-code-review-fixes`、`global-string-trim` | Playwright |
| SC-012 | `vue-tsc --noEmit` 中**本次改动的前端文件零错误**（全局存量基线约 39 个错误不作门槛） | 本地 |

## 七、非目标（Out of Scope）

- **OUT-1**：不改动合同编号的**模糊搜索**能力（INV-1）。判重另起独立语句，绝不「顺手」把 `ContractMapper.xml:9` 改成精确匹配。
- **OUT-2**：不做合同编号的**格式校验 / 编码规则校验**（长度、前缀、年份段等）。本特性只管「不重复」，不管「编得对不对」。
- **OUT-3**：不主动清洗存量的 33 条脏值（31 条空串 + 2 条字面「无」）为 `NULL`。它们由数据库侧的条件生成列表达式统一映射为 NULL，不影响约束正确性；改写字面值属于数据订正，需业务方单独确认（见 OQ-2）。
- **OUT-4**：不处理**软删记录之间**的编号重复（如实测中一号三行的那组）。软删记录不参与约束。
- **OUT-5**：不提供「确认后仍然保存」的旁路（FR-11 明确禁止）。也不提供管理员豁免。
- **OUT-6**：不改造 `checkContractNameUnique`（合同名称校验）。它的空值语义（空→false）与本特性无关，保持现状；两者的差异记为已知不对称。
- **OUT-7**：不改 `@DataScope` 在合同列表查询上的语义。判重是**新增的独立查询**，不经数据权限；既有列表查询的数据权限行为一行不动。
- **OUT-8**：不做 Excel 导入侧的判重。`ContractController` 只有 `/export`，**没有导入入口**（已核实全部 mapping）。
- **OUT-9**：不改造 `pm_contract` 的软删策略。合同继续用软删，不改硬删。
- **OUT-10**：不涉及付款、项目、收入确认等下游模块的任何行为。

## 八、假设与待确认

### 已拍板的业务决策（作为约束写死）

| 决策 | 内容 |
|---|---|
| D-A | 合同编号**保持非必填**，多条空编号合法共存 |
| D-B | 空值（NULL / 空串 / 字面「无」/ 纯空白）**不参与判重** |
| D-C | 重复时**硬拦截**，无「确认后放行」后门 |

### 假设

1. **字面「无」等价于未填写。** 依据：生产存在 2 条 `contract_code='无'` 的记录，语义上是录入人员用中文表达「没有编号」，与空串同类。
2. **重复录入是缺陷而非业务场景。** 依据：258/263 两条记录的客户、类型、状态、金额、签订日期完全相同，由两个部门的两人分别录入；不存在「同编号补充协议」这类合法多行语义。
3. **软删记录不占用编号。** 依据：软删是业务撤销动作，撤销后编号应可复用；且裸唯一索引在存量 5 组冲突下根本装不上。
4. **本地开发库与生产 schema 漂移一致**（都缺 `uk_contract_code`），故 DDL 变更脚本可在两处使用同一份，但**存量冲突数据不同**（本地 258/263 仍双双在用），迁移前必须各自跑一次前置检查。
